vfp CLI + Browser Workspace

LLM VFX
Orchestrator

Autonomous VFX pipeline: local-first shot planner for model-agnostic prompts + Python vfp CLI for closed-loop LLM/ComfyUI orchestration with QA, corrections, retries and persisted job state.

Arquitectura en dos partes

Planificación local,
ejecución orquestada.

El workspace del navegador prepara la entrega; el CLI la ejecuta con bucle cerrado.

1. Browser Production Workspace

Planificador de shots local-first que convierte project bible + shot spec en prompts reproducibles y model-agnósticos. Sin API keys, sin llamadas externas.

  • Secuencia coherente de 4 shots desde el inicio
  • Reglas visuales globales + campos por shot (cámara, movimiento, iluminación, continuidad, referencias, negative-prompt, seed)
  • Ensambla prompt completo desde campos explícitos; nunca lo envía a servicios remotos
  • Marca información crítica faltante antes del handoff
  • Estados: planned → prompt-ready → in-review → approved + runtime planeado
  • Import/export manifestos JSON versionados para backup y handoff
  • Edits en localStorage; exporta manifiesto para backup portátil

2. Python Orchestration Package (vfp CLI)

Capa de ejecución: coordina agentes LLM + ComfyUI, trackea estado del job, QA, correcciones acotadas, reintentos y reportes machine-readable.

  • Acepta workflow JSON, briefs en lenguaje natural y templates nombrados
  • Config YAML + env vars para proveedores LLM y ComfyUI (credenciales solo en env/secret manager)
  • Bucle cerrado: Director → ComfyUI (queue + WS con deadline duro + fallback /history) → QA Inspector (score/issues normalizados) → Correction Agent (patch graph) → repeat
  • Para en max_retries (default 3), plateau (min_score_improvement, plateau_patience) o no-op patch
  • Estados finales: completed, escalated (human review, escalation_reason persistido) o failed
  • Fallbacks LLM (llm.fallbacks) mantienen el pipeline vivo si un proveedor degrada
  • Concurrencia acotada: pipeline.concurrency, qa_concurrency, comfyui.max_concurrent_renders

Capabilities

Diseñado para producción
VFX real, no demos.

Cada feature resuelve un problema concreto de pipeline: handoff limpio, calidad verificable, resiliencia.

Manifestos JSON versionados

Backup e handoff portátil entre browser workspace y CLI. Schema estable, migraciones explícitas.

Model-agnostic prompts

El workspace no asume compatibilidad universal; produce spec transparente que el Director adapta al modelo objetivo.

Bucle cerrado con QA

Vision QA inspecciona renders (base64), devuelve score/issues normalizados. Correction Agent parchea el graph ComfyUI.

Resiliencia por fallbacks

llm.fallbacks: [glm, qwen] + corrección de errores de ejecución ComfyUI (OOM, bad node) mantiene jobs vivos.

Concurrencia acotada

Jobs paralelos (-j N), QA fan-out por job, límite duro de renders concurrentes en ComfyUI.

Estado persistido duradero

Job store en ~/.vfp/jobs (o $VFP_HOME). Historial completo, recuperable, auditable.

Feedback Loop

Cómo funciona el
bucle de corrección.

Seis pasos deterministas, cada uno verificable y con límites duros.

  1. Director genera workflow JSON ComfyUI desde prompt + template + asset hints.
  2. ComfyUI ejecuta el render; cliente sigue queue + WebSocket con hard deadline (default 3600s WS) y fallback /history si el socket cae.
  3. QA Inspector recibe imagen renderizada (base64) y retorna score normalizado + issues estructurados.
  4. Correction Agent parchea el graph (inputs, add/remove nodes) si quality < threshold (qa_threshold default 0.8).
  5. Repetir pasos 2–4 hasta max_retries (default 3); parada temprana en plateau (min_score_improvement 0.01, plateau_patience 2) o patch no-op.
  6. Finalizar job como completed, escalated (human review, escalation_reason persistido) o failed.

Templates listos

Arranca en segundos,
personaliza sin fricción.

FAQ

Preguntas frecuentes

¿Cómo arranco el browser workspace?

Requiere Node ≥ 18.17 y pnpm (anclado vía corepack): pnpm install --no-frozen-lockfile y pnpm dev. Verificación completa: pnpm run check && pnpm test && pnpm run build.

¿Cómo instalo el CLI vfp?

Desde source (no está en PyPI): python -m pip install -e '.[dev]'. Luego vfp --help y vfp run --help.

¿Necesito API keys para usar el browser workspace?

No. El workspace es local-first, no llama a ningún LLM ni servicio externo. Las API keys solo las necesita el pipeline Python (config YAML + env vars).

¿Qué proveedores LLM soporta el pipeline?

Claude (Sonnet 4), Qwen-VL-Max, GLM-4V-Plus configurables en YAML; fallbacks encadenados. Cualquier endpoint OpenAI-compatible (Ollama, vLLM, Groq, Gemini…) vía llm.providers.

¿Cómo configuro ComfyUI?

En YAML: comfyui.host, port, timeout, ws_timeout, max_concurrent_renders, use_proxy. También api_url para remoto detrás de reverse proxy. Env overrides: VFP_COMFYUI_*.

¿El pipeline garantiza que un prompt funciona en cualquier modelo?

No. El workspace produce un handoff spec transparente; el Director adapta al modelo objetivo. La compatibilidad universal no se reclama ni se prueba.

¿Cómo mido capacidad sin GPU?

python scripts/benchmark.py --jobs 24 --render-ms 50 --qa-ms 20 --images 2 --concurrency 1,2,4,8 usa un stand-in HTTP+WS ComfyUI local.

¿Dónde se guarda el estado de los jobs?

Por defecto en ~/.vfp/jobs (o $VFP_HOME / VFP_STORE_DIR). Historial duradero, recuperable, auditable.

¿Qué licencia tiene el proyecto?

MIT — ver LICENSE. Nota: pyproject.toml aún declara Apache-2.0; el archivo LICENSE (MIT) es el autoritativo.
